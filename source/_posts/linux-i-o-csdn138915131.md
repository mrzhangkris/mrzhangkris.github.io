高负载服务器的磁盘 IO 打满时，除了换硬件，还有一个内核参数值得试：I/O 请求队列长度 `nr_requests`。它决定每个块设备能同时排队多少个请求，调大之后多任务场景下磁盘调度余地更大，延迟往往能降下来。这篇记录在 CentOS 上查看和调整它的方法，查看与调整动作在 Rocky 9 容器实测过，实测同时暴露了一个"写不进去"的坑，一并给出。

## 实验环境

- Rocky 9 一次性容器（内核 5.14），真机 CentOS 7 同样适用；
- 实测对象：容器可见的 vda（虚拟盘，默认 256）与 loop30（loop 盘，默认 128）；
- iostat 来自 sysstat 12.5.4。

## 请求队列长度影响什么

Linux 里每个磁盘设备都有自己的 I/O 请求队列，队列长度就是设备可以缓存的请求数量。队列更长，内核就能把更多请求攒在一起做调度和合并，在高负载、多任务的环境下效果明显；代价是管理这些请求需要消耗更多内存——每个排队请求都占内核内存，队列翻倍内存开销跟着翻倍。

一句话机制：**nr_requests 是调度器的"原料池"，池子大，合并与重排的空间才大**。

顺带认识同目录下的邻居 `read_ahead_kb`（实测默认 128，单位 KB）：预读大小，决定内核在一次读请求后面"顺手"多读多少。顺序读为主的负载（大文件拷贝、日志扫描）调大它往往比调 nr_requests 收益更直接，两个参数经常一起评估。

## 实例一：查看当前值

直接读 /sys 文件系统：

```bash
# 查看当前的请求队列长度
cat /sys/block/sda/queue/nr_requests
```

实测（vda 是虚拟盘、loop30 是回环盘，默认值各不同）：

![配图1](/images/csdn/figures/linux-i-o-csdn138915131-1.png)

**验证点**：命令输出一个数字（SATA/SAS 真实盘常见 128，NVMe 常见 1023/1024），先记下这个基线再动手。

## 实例二：调整

写同一个文件即可调整，原文做法是调大观察：

```bash
# 设置请求队列长度为 256
echo 256 > /sys/block/sda/queue/nr_requests
```

实测中撞到一个边界：**不是所有设备都接受调大**。在 loop 盘上把 64 调小成功，往回调 256 直接被内核拒绝：

![配图2](/images/csdn/figures/linux-i-o-csdn138915131-2.png)

`Invalid argument` 且原值不变——内核拒绝时不会写坏任何东西，但如果命令写在脚本里没检查退出码，就会以为调成功了。真实 SATA/SAS 盘上从 128 调到 256 通常可行；虚拟化环境（virtio、loop）的队列深度受虚拟化层约束，可能不接受。

**验证点**：`echo` 后必须再 `cat` 一次读回确认，看到目标数字才算改成功。

注意这条写的是运行时状态，重启即失效，确认有效后需要写入 udev 规则或开机脚本做持久化。

## 实例三：用 iostat 观察效果

调整的价值要用数据确认。每 2 秒刷新一次、共 5 次：

```bash
# 每 2 秒刷新一次，共刷新 5 次
iostat -dx 2 5
```

实测输出（sysstat 12.5.4）：

![配图3](/images/csdn/figures/linux-i-o-csdn138915131-3.png)

对照方法：调队列前后各采一组，重点看三列——`await`（单次 IO 平均等待，主指标）、`aqu-sz`（队列平均深度，验证调大的队列是否真被用上）、`%util`（盘忙碌占比，长期逼近 100% 说明盘本身是瓶颈，调参数救不了）。同时开着 `top` 盯内存，确认调整没有拖累其他部分。

## 使用场景

- 高负载服务器：数据库服务器、文件服务器这类 IO 密集型服务，调大队列长度通常有收益。
- 多任务环境：多个 IO 密集型应用同时跑时，更长的队列能改善响应时间和处理效率。

反过来说，低负载机器调它没有意义——队列根本排不满，合并无从谈起。

## 错误写法对比

**错误一：echo 完不检查**。`echo 256 > ...` 被内核拒绝时 shell 会报 write error，脚本里不看退出码、不再读回确认，调整就成了"以为生效了"。

```bash
# 错：写完就走
echo 256 > /sys/block/sda/queue/nr_requests

# 对：写完读回验证
echo 256 > /sys/block/sda/queue/nr_requests && cat /sys/block/sda/queue/nr_requests
```

**错误二：把 nr_requests 当独立开关调**。它和 I/O 调度器、单请求大小共同决定行为，队列调大但调度器不匹配盘的类型，收益可能为零甚至倒退。

## 注意事项

- 调整任何系统设置前先备份原值（就是实例一的 cat 输出），操作尽量安排在低峰期。
- 先在测试环境验证效果，再考虑上生产，调大不一定都是正收益。
- 队列长度和内存占用成正比，内存紧张的机器上调大可能导致整体性能反而下降。
- 这个参数和 I/O 调度器是配合关系，调队列长度时留意当前调度器是否匹配盘的类型。

## 小结

回到开场的 IO 打满：nr_requests 给的是"调度余地"这张牌——先 cat 基线，echo 后读回验证，再用 iostat 的 await/aqu-sz 确认收益。实测提醒两件事：不是所有设备都接受调大（Invalid argument），以及调大生效不等于调大有用。这张牌打完还没起色，再考虑换硬件也不迟。
