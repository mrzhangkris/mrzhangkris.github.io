# 我给 AI 搭了一条博客产线，然后被首篇文章教育了

> 你现在读的这篇，是产线写完第一篇真文章之后，回头写的第二篇。题材就是产线本身：怎么选技能、怎么编排、怎么在第一次实跑里被现实教育，又怎么把教训长回产线里。

## 产线长什么样

先交代结构。一条文章的生命线是：研究 → 写作 → 润色 → 发布。前三个环节各有专门技能负责——研究大纲归 content-research-writer，润色重写归 write，去 AI 味归 humanizer-zh（它背后是维基百科那页"AI 写作特征"清单，专治三段式排比、夸大象征这类机器腔）。这些技能不是我写的，是现成的。

我要补的是两块：一块叫编排，一块叫闸门。

编排就是一个叫 blog-pipeline 的技能，它自己不写一个字，只干一件事：看你处于哪种场景，把对应的子技能按需叫出来。写新文章走全流程；改旧文走 edit-article；只润色现成稿子就跳过前面直接进润色闸。它像个领班，不炒菜。

闸门是个脚本，后面细说。

## 设计决策：编排器保持薄

搭编排层时唯一纠结过的点是：要不要把子技能的指令复制一份进编排技能。复制了，编排技能就自包含，单独看很完整。

没复制。理由很实际：同一份指令存两处，改一处忘另一处，漂移只是时间问题。子技能升级了，编排里的副本还停在旧版，到时候跑的是哪套规则没人说得清。所以编排技能里只有路由表和场景判断，子技能内容一律现场加载。它瘦，但不会过期。

## 把纪律变成代码

agent 有个毛病：技能读了，执行时会飘。你跟它说 date 必须早于推送时刻，它今天记得，三周后的深夜赶稿未必记得。所以纪律不能只写在给人看的文档里，得变成跑得起来的代码。

于是有了 check_post.py，零依赖，发布前必须过它。它查的东西每一条都对应一次真实的疼：

- **文件名必须纯 slug，禁止日期前缀**。这条的来历最典型。站点 permalink 是 `:year/:month/:day/:title/`，我起初想当然以为 `:title` 取自 front matter，拿 curl 一测才发现它取的是文件名——如果文件名叫 `2026-09-11-xxx.md`，产出的 URL 就是 `/2026/09/11/2026-09-11-xxx/`，日期出现两遍。发现后这条就从"约定"升级成了正则拦截。
- **date 必须早于推送时刻**。留着 5 分钟余量，吸收构建排队时间。
- **正文非空、title/date 必填**这类底线检查，防手滑。

FAIL 就是 push 不了，没有商量。警告类（比如中文 slug）才允许带着说明通过。

## 首篇实战：产线被教育

设计得再顺，第一次真跑才知道哪疼。首篇是重写我 2024 年在 CSDN 的一篇 CentOS 旧文，全过程挑几个说。

**技能口径过期了**。这套技能最早按 Jekyll/Chirpy 的规矩写，而站点前一天刚迁到 Hexo/Butterfly。发布前一对，校验器、front matter 模板、流程说明三处全是旧口径。好在闸门的哲学就是"发布前必查"，问题在发布前暴露，回头把三件套全改到 Hexo 版。这也反过来验证了那句话：纪律写进代码，比写进文档可靠——文档过期了没人知道，代码过期了会当场报警。

**配图的"真实输出"原则**。文章讲 Linux 命令，截图里的数值不能编。我的机器是 macOS，于是起 Docker 容器实跑命令抓真输出；容器选了 Rocky Linux 9 而不是 Ubuntu，因为文章语境是 CentOS 的后继者，图里出现什么发行版是有讲究的。输出有了，还要渲染成统一的终端窗风格。渲染脚本写了两版：第一版中文全是方块——后来才明白 Menlo 这类等宽字体压根没有中文字形，注释里的中文得自动切到中文字体渲染，ASCII 和中文分段各用各的。还有个小坑：拿视觉模型给渲染结果做质检时，它会把方块区域一本正经地"脑补"成一段根本不存在的中文。报告里说"有方块"可信，引用它认出的具体文字之前，得先对着源文件核实。

**缩略图的教训最直接**。我给首篇配了张终端风格的题图当封面，自我感觉良好。发布之后收到反馈：缩略图不要用文章里的图。换了一张 Unsplash 的深色代码屏，然后这条要求当场固化：每篇文章必须单独配缩略图，禁止复用正文插图，写进 front matter 模板，校验器加了两条 FAIL——缺 cover 拦下，cover 和正文图重复也拦下。今天这篇的缩略图就是按这条新规矩选的，产线自己给自己定的第一条纪律。

## 发布之后还有一课

push 完、构建绿、文章 URL 返回 200，我以为结束了。去首页一看，没有新文章，吓一跳，回头一查——其实首页早就有，是 GitHub Pages 的 CDN 缓存还挂着 10 分钟窗口。这不算 bug，但值得记住：**部署验证要直接 curl 文章 URL，别只看首页**。这条也进了技能的检查清单。

## 产线是长出来的

回头看重心：这套产线没有一天是"设计完成"状态。选技能和编排是它的骨架，骨架搭完只能算能用；真正让它开始可靠的，是每次实跑暴露一个盲区，然后修掉、沉淀、把对应的检查机械化。文档会过时，人会忘，只有跑在发布必经之路上的脚本不会放过任何人。

这篇是产线的第二次实跑，也是第一个"由产线记录产线成长"的产物。下一疼出现的时候，大概又是一条新红线的出生证明。
