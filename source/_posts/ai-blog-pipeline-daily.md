9 月 11 日发过《博客产线（一）》：一条「研究 → 写作 → 润色 → 发布」的技能编排产线，编排骨架到今天还在用。但上线后两个月的真实数据是：10 月发 2 篇，11 月到现在 0 篇。产线不缺产能，缺订单——触发权一直在我手里，我一忙，产线就停。今天（2026-11-24）产线（二）上线：触发权交给定时器，每天 09:07 自动跑完整条链；验证不过，一律不发。你现在读到的这篇，就是链路试跑的第一件产品。

## 一代卡在哪

先用数据把问题钉死。9 月 11 日产线（一）上线，当月借 CSDN 迁移集中补了 19 个提交的存量；10 月新增 2 篇；11 月至今 0 篇。这些数字来自仓库的 git 提交记录（`--diff-filter=A -- source/_posts/`），可复核。

问题不在写作环节——潤色、配图、双语，各环节工具都在。断点在第一个环节之前：没有人或东西负责「今天写什么」。技能编排解决的是「怎么写」，定时触发解决的是「什么时候开始写」。二代要补的就是这一块。

## 二代架构：五层流水线 + 一本台账

整条链由一个定时任务驱动，每天 09:07 起一个独立会话，按固定顺序执行五层，外加一本状态台账：

| 层 | 职责 | 判定标准 |
|---|---|---|
| 选题 | 台账去重 + 三个素材源 | 不与台账及站点既有标题撞车 |
| 写稿 | 按写作基准线写中英双份 | 类型判定 + 篇幅口径 + 禁机器腔 |
| 验证 | 本地构建 + 双语对账 | 构建退出码 0 且无 ERROR |
| 发布 | 定向 add、规范 commit、push | push 后跑 19 项线上回归 |
| 记账 | 台账追加一行 | 可追溯，封面不重复使用 |

先说时间点为什么是 09:07。定时任务在整点扎堆容易互相挤占——之前另一条定时产线上有过同刻到期被串行任务挤掉窗口、直接跳到第二天的实测教训，所以错开整点取 09:07。每天一篇是发布频率的约定，具体时刻属于可调参数。

## 选题：一本台账，三个素材源

去重靠台账。产线配了一个状态文件（`选题台账.md`），动笔前必读：已发布表的题目和 slug 不许重复，「失败/跳过记录」里的题目也要避开；同时 grep 站点既有文章标题防撞车。标题决定了文章的永久链接，撞车即断链，这道检查放在最前面。

素材源按优先级排三档：

1. **Agent 自进化实验目录**：一组按日期归档的实验（selforg、memrecall、skill-erosion 等），每个实验都有预注册、跑批记录和结论，是现成的复盘素材。
2. **插件与技能工作区的最近改动**：门禁插件、网文产线、各类技能的踩坑与修复记录。
3. **记忆库检索**：长期记忆里的焦点任务、修复记录、裁决，适合补「决策为什么这么做」的背景。

优先级即素材密度：实验目录里一个完整实验的预注册、数据、结论，通常就够一篇项目复盘的骨架。

## 写稿：基准线 + 双语 + 封面池

写稿不是自由发挥，三样东西是硬约束。

**写作基准线。**动笔前先判定文章类型——一篇只属一类，然后按类型的篇幅口径写（项目复盘 2000-4000 字，观点随笔 800-2000 字），通用纪律六条照办：技术保真（命令、配置、版本原样）、诚实边界（没实跑的直说）、结论先行、段首主题句、主动语态、禁机器腔（「总而言之」「值得注意的是」这类起手式直接毙）。

**双语双份。**这是站点自己的回归断言：中文站和英文站文章数必须一一对应，缺一篇回归就报红。所以每篇产线稿天然是两份文件——`source/_posts/<slug>.md` 和 `site-en/source/_posts/<同slug>.md`，同名同日期，英文版 frontmatter 多一个 `lang: en`。

**封面池。**每篇文章的封面从一个按主题分类的图片池里选，已用过的 id 在台账登记，不许复用。选之前先 grep 全站确认没被别处引用过。

## 验证与发布：验证不过，一律不发

发布闸门只有一条规则：**验证不过，不 push**。具体判定两条：本地 `hexo generate` 退出码 0 且输出无 ERROR 行；中英文章数相等、新文章同名同日期。两条全过才进发布层。

发布层本身也有纪律。`git add` 只加两份新稿的具体路径，不许 `git add -A`——防止把无关的本地状态文件带进仓库；commit 信息固定格式 `post: <中文标题>`；push 用 `git -c http.sslVerify=false push origin main`——这条不是偷懒，是这台机器对 GitHub 的 SSL 验证有历史故障，前人已把绕过方式固化成流程。push 之后等约 90 秒，跑一遍 19 项线上回归（关键路径 200、双语对账、sitemap、机器人接口），有红项就修复重推。

万一验证卡住怎么办：重试上限 2 次，仍不过就把失败原因写进台账的「失败/跳过记录」表，当天不发。宁可缺刊，不发坏稿。

## 首篇试跑实录

本文就是试跑产品，但如实交代：它不是定时任务自己写的，而是上线前的一次人工试跑——由我拍板启动会话，走的是与定时产稿完全相同的五层链路。试跑验证了三件事：

1. **链路完整可走通**：台账初建、封面池选号（本文封面 photo-1600132806370-bf17e65e942f，cloud 分类，grep 确认全站未用）、双语对账、本地构建、push，全部通过。
2. **去重机制有效**：选题时发现站点已有一篇《博客产线（一）》，处理方式不是绕开，而是入列同一系列（`series: blog-pipeline-line`）做续篇——去重检查的本意就是逼出这种关系。
3. **日期陷阱已排**：站点的永久链接按 UTC 落日期，北京时间凌晨发文会把文章落到前一天。本文 date 写 09:07:00，正好避开。这个坑之前有过一次实测修正（一篇 9 月的文章发文后发现日期落错，专门提交过一次修复），这次直接写进了产线规范。

定时任务从明天（11-25）09:07 开始每天自动跑。之后产线每跑一天，台账多一行。

## 还没检验的东西

三个问题留给时间：

- **机器腔压不压得住**：基准线和验证脚本管格式与事实，管不了文风。每篇文章的文风是否过关，要等读者反馈和回看抽查。
- **素材池续航**：实验目录 7 个、插件工作区若干、记忆库常更新，按每天一篇的消耗速度能撑多久，一个月后见分晓。
- **失败台账还是空的**：「失败/跳过记录」表还没有样本，真失败了才知道流程哪里最脆。

产线（三）预定一个月后写：成稿率、素材消耗速度、质量抽查结果，用数据说话。
