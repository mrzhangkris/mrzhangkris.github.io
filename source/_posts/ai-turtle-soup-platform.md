海龟汤是一种聚会推理游戏。出题人抛出一个离奇的汤面，比如"他每天都吃企鹅肉，吃完就哭了"，玩家只能提用"是"或"否"回答的问题，一点点逼近汤底。这个游戏的乐趣全押在出题人身上：他知道全部真相，还得守住秘密。

我想，这件事 AI 天然就擅长。它读过的悬疑故事比任何人类出题人都多，不累，不剧透，随叫随到。于是有了 soup.jianshi.xyz，一座从一锅海龟汤长出来的悬疑游戏平台。截至 2026-09，它有三种玩法、三本原创真人剧本杀、70 道单机汤题，微信支付真实跑通，660 多个后端测试守着部署门禁。

这篇文章复盘这座平台怎么长出来的，以及让 AI 扮演一个会撒谎的凶手，需要哪些设计。

## 三种玩法，一条商业化

平台首页是暗色的终端风格，三种玩法并排摆着，共用同一套账号和会员体系。

第一种是经典汤面推理。30 道精修题库，点开就玩。每一次提问，AI 实时判定"是 / 否 / 无关 / 是也不是"，判定依据是它对汤底的理解。卡住的时候可以要提示，觉得还原得差不多了，就用自由文本写出你心中的真相，AI 给出评分和点评。它还会现场出题：输入主题和难度，生成一道全新的汤。会员可以定制私人汤，把自己的名字和梗织进谜题。想跟朋友玩就开好友房间，8 位房间码加入，主持人卡壳时还有"AI 替我答"递上判定建议。

![经典汤面对局：提问、判定、逐步逼近汤底](/img/ai-turtle-soup-platform/04-soup-play.png)

第二种是单机沉浸剧本杀《雨夜旅馆》。五幕原创剧本，一个人玩的文字冒险：403 房永远显示占用，凌晨 2:14 台灯自己亮起，还有七封白纸信。点击场景搜证，跟 NPC 对话，自由行动交给 AI DM 全权回应。每个角色有独立的 TTS 音色，幕间有"本幕剧本"过场，倒计时归零剧情强行推进，像在玩一场有声剧。

![单机剧本杀《雨夜旅馆》：场景搜证与 AI DM](/img/ai-turtle-soup-platform/07-mystery.png)

第三种是平台的主打，真人 roleplay 剧本杀，也是这篇文章的重点。1 到 5 人开团，空席由 AI 补位，而且 AI 会演，会撒谎。

## 每人一本剧本，AI 补位还演戏

真人局对齐的是线下剧本杀的核心体验：信息不对称。

开局每人领一本只属于自己的角色剧本：公开身份、秘密（标红警示）、逐段时间线、个人任务。秘密按席加密下发，你只能看到你自己的那份。搜证拿到的线索先进自己口袋，公开与否自己决定，也可以跟任何人私聊试探。终局全员投票指凶，无论对错，真相立刻揭晓。

![开局读本：案件读本、五席选择、只属于你的角色剧本](/img/ai-turtle-soup-platform/10-roleplay-script.png)

空席由 AI 角色扮演。关键在于，AI 只持有各自的人物卡，不知道其他人的秘密，所以它会回避、撒谎、转移话题，守着自己的底牌，跟一个真玩家没什么两样。凶手席的 AI 更难缠：哪怕被铁证围困，它也只会按剧本"崩溃"，绝不认罪。

AI 互聊链又把对质往前推了一步。AI 台词里点名了谁，谁就接话。你会看到秀娥把锅甩给林岸，林岸反过来作证，群像对质就这样自己长出来，不需要任何人编排。

![公屏对质：AI 角色互相点名、甩锅、作证](/img/ai-turtle-soup-platform/12-roleplay-chat.png)

![终局投票：指认你认为的凶手](/img/ai-turtle-soup-platform/13-roleplay-vote.png)

对局结束有任务计分复盘：每人 3 条隐藏任务逐条结算，凶手"活着脱罪"另有加分，复盘页里还有完整的调查回放和线索归属，每一步都摆得清清楚楚。

## 让 AI 演得像：角色五件套

真人局里 AI 要演得像人，光靠一句"你是一个客栈老板娘"不够。平台给每个 AI 角色配了五件套，全部写在剧本数据里。

以《守灯人之死》的老板娘秀娥为例，她的回避策略（deny_rules）和铁证补丁（patch_rules）长这样：

```json
{
  "name": "老板娘 · 秀娥",
  "deny_rules": [
    { "about": "摔壶 / 你和他动手了？",
      "say": "「摔的是我自己的壶！」——壶确实是你出门时砸在礁石上的，你认砸壶撒气，咬死没碰过他一根指头" },
    { "about": "你恨他 / 你有杀人动机",
      "say": "「恨？我恨的是那年的灯！」把仇恨引向「灯塔那晚的失职」，而不是老周本人" }
  ],
  "patch_rules": [
    { "if_clues": ["ledger"],
      "say": "（一把按住账本又缓缓松开）「……对，他欠我八千。两年了，年年说下年还。昨晚我就是去要钱的，吵翻了，21 点 38 我摔门走的。我要是想要他命，能等到今天？」" }
  ]
}
```

这套设计的核心思路是行为脚本化，不依赖 LLM 自觉。回避策略（deny）定义被问到嫌疑话题时的口径，剧本写死；铁证补丁（patch）在特定线索公开到线索板的瞬间触发，被戳中的角色当场变脸，说出备好的辩解；崩溃口径（collapse）是决定性证据集齐后的松动台词。触发全部由代码判定，条件是公开线索集合覆盖规则的触发组，LLM 只负责自由问答部分。确定性触发，胜过祈祷模型每次都演到位。

第五件是保险丝。LLM 输出之后还要过一道自认关键词过滤器，"我杀""凶手是我"这类话命中就整体替换成回避口径。最关键的禁忌永远不要指望 prompt 管住，要在输出侧兜底。凶手席的 AI 被玩家用各种话术钓过，没钓出来过一次。

## 秘密是怎么保住的

真人局里另一个要命的问题是信息隔离。五个玩家五条 WebSocket 连接，凭什么张三看不到李四的秘密？

平台把"不泄露"做进了服务端架构。每个连接收到的房间状态，都是服务端按"这个连接是谁"单独组装的个性化快照：私密字段（自己的剧本、自己的线索、自己参与的私聊）只出现在本人的 payload 里。其他角色的剧本和秘密，从一开始就不会进入你的状态数据，也不会进入 AI 的 prompt。前端想渲染也无从渲染，数据根本不在传输链路上。

配套还有一组泄露矩阵测试：以每个席位的视角，断言他人的剧本与秘密绝不出现在我的 state 或 AI prompt 中。这类 bug 靠人眼查不完，得让测试矩阵替你盯着。

回头看，这个项目里最值得复用的经验有两条。

AI 扮演角色的可靠性不靠 prompt 祈祷，靠结构。什么话题回避、什么证据触发什么台词、什么话绝对不能说，全部做成数据里的规则和输出侧的过滤器，LLM 只补自由发挥的部分。

信息不对称这种玩法根基，必须做进架构。按席组装状态、泄露矩阵测试、AI prompt 的信息按需注入，三层加起来才敢说秘密只在该知道的人手里。
