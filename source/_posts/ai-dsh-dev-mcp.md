## 一、AI 写插件的第一问，模型答不了

让 AI 给 dsh 写一个插件，它遇到的第一个问题不是怎么写代码，而是一个事实问题：**宿主到底提供了哪些服务、哪些配置行、哪些挂载点？**

这个问题模型自己答不了。dsh（DeepSeek Harness）是 2026 年才开源的框架，预训练语料里几乎没有它的痕迹；插件的 API 契约、profile 的组合语义、patch 的覆盖规则，全部长在宿主仓库的 docs/ 与 packages/ 里。没有可靠的查阅通道时，模型的补全本能会接管一切——它会用通用插件框架的经验「合理地」编出一份 API，看起来头头是道，一跑全是 `undefined`。

我给花名册插件写文章的时候，切身体验了这个工具的必要性：那篇文章里每一个关于 patch 语义的断言——整体替换而非合并、按 id 后写者赢、空 patch 文件导致启动失败——没有一句是「我记得」，全部来自 dsh-dev MCP 拉回的宿主文档与源码。这篇文章就把这个工具本身拆开讲：它解决什么问题、七个工具怎么组织的、边界画在哪里。

## 二、问题定义：AI 需要的不是文档，是文档的可达性

先说清楚这个工具不是什么。它不是一份「dsh 开发 FAQ」，不是把文档摘要塞进系统提示词的 RAG 管线，也不缓存任何仓库副本。它做的事情用一句话概括：**把宿主仓库的文档树、源码搜索和运行中的宿主服务，暴露成 AI 可以自主下钻的 MCP 工具**。

这个定位来自一个判断：AI 与文档的关系应该和人一样——先看目录，再读全文，读不到就全文搜索，搜不到就换个关键词。预先摘录、预先总结的做法有个致命缺陷：摘要者决定了 AI 能看到什么，一旦摘要漏了关键细节（patch 不做深度合并这种一句话就能让整段代码返工的细节），AI 无从知晓自己缺了什么。dsh-dev 的选择是把「发现」也交给 AI：它只提供通道，不提供结论。

工具实现是能说明问题的：整个 server 是一个 283 行的单文件 `server.js`，零自定义协议。文档读取直接调 `gh api repos/deepseek-ai/deepseek-harness/contents/docs/...`（GitHub Contents API，按需取 base64 解码），搜索直接调 `gh search code --repo=...`。不 clone 仓库意味着永远读到的是 GitHub 上的最新版本，代价是每一次读取都有一次网络往返、依赖本机 gh 认证。对一个个人开发工具来说，这笔账是划算的。

## 三、七个工具的组织：一条从「不知道有什么」到「直接操作」的阶梯

dsh-dev 一共七个工具，按 AI 的工作流排布，恰好构成一条认知阶梯：

| 工具 | 回答的问题 | 底层通道 |
|---|---|---|
| `dsh_docs_list` | 文档目录里有什么？ | GitHub Contents API 列 docs/ |
| `dsh_docs_read` | 这篇文档说了什么？ | Contents API 取单文件全文 |
| `dsh_docs_search` | 某功能在哪实现了？ | GitHub code search，限 20 条 |
| `dsh_service_status` | 本机宿主跑起来了吗？ | launchctl / 端口探测 / 日志统计 |
| `dsh_sessions_scan` | 本地会话积压了什么？ | 解压 zstd 会话日志逐条判定 |
| `dsh_web_token` | web 界面怎么解锁？ | 从 web-stdout.log 抓最新 token |
| `dsh_rpc_call` | 宿主服务的方法怎么调？ | 经 dsh-rpc-bridge 插件 HTTP 透传 |

前三个是「读仓库」，中间三个是「看本机」，最后一个是「动宿主」。这个次序不是随便排的——它就是调试一个 dsh 插件问题的真实动线：先查文档确认契约，再看本机服务状态，最后才对运行中的宿主动手。

粒度上也刻意保持了一工具一事。没有「dsh_docs」这种大杂烩工具——列目录、读全文、全文搜索是三个独立工具，因为它们对应模型三种不同的意图：我不知道有什么、我要看这个、我不知道这个在哪。粒度粗了，模型要在一次调用里同时表达多个意图，参数表会膨胀，错误率跟着涨；粒度细了，工具名本身就是工作流。

阶梯的设计意图也写在每个工具的描述文本里。`dsh_docs_list` 的描述是「开发 dsh 插件前先浏览」，`dsh_service_status` 的是「dsh 相关开发调试的第一步」，`dsh_rpc_call` 的描述则直接内嵌了一份速查：「常用服务：agentPresets(list/select)、settings、sessions 相关控制器」。这些描述文本是给模型看的路标——模型选择工具时读的就是这些话，把常用路径写进描述，等于把一条推荐路线预置进了工具选择的那一刻。

## 四、三个实战细节：无命中、错误消息、搜索边界

光看设计图体会不到这种工具的实际手感，说三个我真实遇到的细节。

**第一个是搜索无命中怎么处理。** 写上一篇文章时我第一轮搜的就是 `cordis.patch.yml bundle`，返回的是一行错误：「无匹配（仅索引 docs/ 与 packages/ 下的文本文件；试试其他关键词）」。这行提示半句道歉半句教学——它告诉我 GitHub code search 对这类文件的索引边界，也暗示了正确动作。我换成 `patchReload`，立刻命中 20 条，其中就有 `packages/bundle/base/cordis.patch.yml` 和 `packages/boot/app-boot/src/profile.ts` 这两个后来立了大功的源码文件；再换 `cordis`，命中 `docs/cordis-primer.zh.md` 和 `docs/user/develop/practice/dynamic-cordis.zh.md` 两篇正主文档。**AI 排错的很大一部分是关键词工程，把「索引范围」写进错误消息，等于在 AI 走错路的时候递了张地图。**

**第二个是错误消息即导航。** `dsh_docs_read` 传进去一个目录路径，返回的不是报错堆栈，而是「该路径是目录，请用 dsh_docs_list 浏览」——下一动作直接给在错误里。`dsh_rpc_call` 更进一步，工具描述里承诺「method 名不对时错误信息会列出可用方法」。这类设计在人类工具里叫「可恢复错误」，在 AI 工具里的价值翻倍：模型不需要理解错误理论，它只需要被告知下一步。

**第三个是读的范围刻意收窄。** `dsh_docs_read` 只支持读单文件、只处理 base64 编码，`dsh_docs_search` 只回路径不回内容，要看内容必须再调 `dsh_docs_read` 且只对 docs/ 下的命中有效（源码命中要换别的方式看）。这些限制让工具组合天然形成「搜索定位、读取确认」的两步节奏，防止模型拿一次模糊搜索当结论。

## 五、RPC 透传：从「看」到「动」的那道门

七个工具里，`dsh_rpc_call` 的地位特殊，因为它跨过了只读边界。它的实现路径颇能说明「透传」二字的分寸。

第一版的头注释里写着一条明确的设计决策：「全部基于已验证路径（gh api / 文件系统 / launchctl / 端口探测），**不依赖 dsh-web 的 Typert RPC wire 协议（v2 再考虑透传）**」。也就是说，作者刻意让第一版绕开宿主内部 RPC 协议，只做零依赖的旁路观察。真正的透传后来加了，但实现方式很克制：它不直接说宿主协议，而是把请求 POST 给运行中的 dsh-web 的 `/plugins/dsh-rpc-bridge/invoke` 端点，body 就是 `{ns, method, args}` 三个字段——**协议细节全部留在 dsh-rpc-bridge 插件那一侧，dsh-dev 只做认证（从 web 日志抓最新 token、cookie jar 登录、用完即删）和转发**。

这个分层带来的直接后果是能力边界清晰：`dsh_rpc_call` 能调什么，完全取决于 dsh-rpc-bridge 插件暴露了什么服务面。dsh-dev 自己不维护任何「宿主方法白名单」，也不翻译任何语义。它更像一根带绝缘皮的接线——电压多少，由另一头决定。

把七个工具串起来用，就是一个完整的调试闭环，我验证 RPC 边界时的实际顺序是这样的：先 `dsh_service_status` 确认 dsh-web 进程活着、端口有响应——工具描述说这是「第一步」，确实该是第一步，因为后面所有对运行时宿主的调用都以它为前提；确认无误后再对 `dsh_rpc_call` 发试探性的调用，拿宿主侧的原始报错来反推服务面的真实形状。**观察、查证、操作，三个动作各归各的工具，不混在一起**——这比一个大而全的「dsh 调试」工具好用得多，因为模型可以按需选取，不必每次都理解一整套参数。

我对这条边界做过一次实证：故意调一个不存在的服务 `nonexistentService.list`，返回的是一层不加工的错误 `service not found: nonexistentService (tried nonexistentService)`。报错就是桥和宿主两层各自的真话，没有缓冲层替你翻译。这让排错时看到的信息和宿主进程里发生的事严格一致——代价是错误消息的可读性完全依赖宿主侧的品质，好处是永远不会出现「桥接层善意翻译导致语义漂移」。

## 六、价值与不做的部分

回头看，这个工具解决的核心问题可以总结成一句：**把「AI 猜宿主」变成「AI 查宿主」**。它的价值不在任何单个技术点——gh api 谁都会调——而在三个工程判断的组合：文档不摘录、发现交给 AI、错误消息当路标。这三个判断让它在「AI 开发者体验」这个尚无成熟方法论的领域里，提供了一个可复制的小样本。

同样值得记录的是它不做的部分。它不做写操作——宿主仓库它只读，运行中的宿主它只能经 dsh-rpc-bridge 调方法，文件系统只碰会话日志和 web 日志两处。它不做缓存——没有本地文档副本，断网即失效。它也不试图理解 dsh 业务——七个工具里没有任何一个内置「插件该怎么写」的知识，那些知识仍然住在仓库的 docs/ 里，工具只负责把 AI 带到知识面前。

这其实是给「给 AI 造工具」这件事的一个朴素答案：工具的价值密度不取决于它塞了多少知识，而取决于它让 AI 离一手事实有多近。我在花名册系列里引用的每一条宿主行为，都可以沿着 `dsh_docs_search` → `dsh_docs_read` 的路径复核——证据链可追溯，这是这个 283 行的小工具给出的最大价值。

## 七、还没搞清楚的两个问题

一是 `dsh_sessions_scan` 的会话判定逻辑（从 zstd 压缩的会话日志里解出 origin/mode/ended）标注为「pruner 同款」，但与宿主内置 pruner 的实现是否严格一致、日志格式变更时谁先感知，我没有对照验证过；二是 `dsh_rpc_call` 的 token 抓取依赖 web-stdout.log 中的 URL 格式，dsh-web 的认证方式若变化（比如改用非 query 参数传递），这条通路会静默失效——目前没有探测到失效的告警机制。

工具本身还在演化，v2 是否真的把 wire 协议透传做进去、会不会增加写通道，都还是开放问题。但第一版立住的那条原则应该不会变：AI 改插件之前，先让它读到宿主的真话。
