在服务器上敲错一个 `rm -rf` 的代价可能是一整块数据盘。与其事后恢复，不如提前把 rm 这类高危命令在 shell 层面拦住。这篇用 alias 做两层防护：把 rm 换成无害提示，再用定时脚本清理"回收站"，顺带把 shutdown/reboot 这类误触即发火的命令一并禁掉。所有行为在 Rocky 9 容器实测，原文方案的两个坑（嵌套拦截、清理周期语义）在实测中标出并给出修正。

## 实验环境

- Rocky 9 一次性容器，bash 5.1、findutils 4.8；
- alias 生效条件是**交互 shell**，实测用 `bash -ic` 模拟登录后的操作终端；
- `/etc/profile` 对登录 shell 生效，`.bashrc` 对每个交互 shell 生效，生产二选一（影响面见注意事项）。

核心机制一句话：alias 是 shell 的命令替换，发生在回车解释阶段——它防的是人手滑，脚本和定时任务完全不受它管。

## 实例一：拦截 rm

编辑 `/etc/profile`，结尾添加：

```bash
######  rm prevent  ######
alias rm='echo can not use rm command'
```

之后执行 `source /etc/profile` 生效。实测：敲 `rm` 后文件原封不动，只打印一句提示。

![配图1](/images/csdn/figures/linux-csdn138787427-1.png)

两处放置位置的区别：`/etc/profile` 只在用户登录时读一次，影响**所有用户**；放 `~/.bashrc` 则只影响单个用户、每个新开的交互 shell 都会加载。想全机拦截用 profile，只管住自己用 bashrc。

此时文件删不掉，但生产上总归有要删的时候——这就轮到"回收站"方案。

## 实例二：保险删除 rmf

替代思路：把要删的文件先挪到指定目录（如 `/data/recycleDir/`），再由定时任务统一清理；确认删除用另一个别名，保留 `-i` 交互确认。日常"删"文件的动作就变成挪文件：

```bash
# 日常删除 = 挪进回收站
mv /data/app/old.log /data/recycleDir/

# 确认真的要删（保留 -i 交互确认）
alias rmf='rm -i'
```

**实测发现原文写法有一个坑**：`rmf` 展开成 `rm -i` 后，`rm` 又会被第一条 alias 拦截——保险删除自己也删不了文件。修正：用绝对路径绕过 alias：

```bash
# 修正写法
alias rmf='/bin/rm -i'
```

## 实例三：回收站与定时清理

配套的清理脚本 `/data/scripts/del.sh`：

```bash
#!/bin/sh
####################################################
#######    Scheduled file deletion script    #######
####################################################
##   1. Executed every day at 1 am
##   2. Delete files in the /data/recycleDir/ directory
####################################################
location="/data/recycleDir/"
find $location -mtime +48 -type f |xargs rmf -f
```

> 注：alias 在脚本（非交互 shell）中默认不生效，实测脚本里跑 `rmf` 直接报 `xargs: rmf: No such file or directory`。del.sh 里请写完整命令（如 `| xargs rm -f`），否则清理动作不会执行。

**第二个坑藏在 `-mtime +48` 里**。原文注释写"修改时间超过 48 小时"，实测不是：`-mtime +48` 的语义是"修改时间在 49 个完整天之前"（find 按天取整再比较）。49 小时前的文件用它删不掉。要按 48 小时控制周期，用分钟级的 `-mmin +2880`。两种写法的实测对比：

![配图3](/images/csdn/figures/linux-csdn138787427-3.png)

按需选周期后，用 crontab 挂上定时执行：

```bash
0 1 * * * /bin/sh /data/scripts/del.sh
```

## 防止误操作关机

思路相同，把关机相关命令也换成空操作：

```bash
alias shutdown=''
alias init=''
alias reboot=''
```

这些 alias 同样写在 profile 里。真需要关机重启时，把对应 alias 行注释掉，`source` 后重新登录终端即可恢复使用。

## 救急：绕过 alias 用回真 rm

拦截上线后偶尔有必须真删的场景，三个办法按快慢排序：

```bash
\rm file            # 反斜杠跳过 alias
command rm file     # 同样绕过 alias
/bin/rm file        # 绝对路径，万无一失
```

这三个办法也意味着拦截形同虚设——防的是"习惯性手滑"，拦不住"执意要删"，所以回收站兜底层不可省。

## 错误写法对比

**错误一：指望 alias 保护脚本**。定时脚本、`ssh host 'rm ...'` 这类非交互调用都不走 alias，拦截不存在——alias 方案只防交互手滑。

**错误二：`rmf='rm -i'` 嵌套在拦截之下**。展开链 `rmf → rm -i → echo can not...`，确认删除失效（实例二已实测），必须写 `/bin/rm -i`。

## 注意事项

- alias 只对交互 shell 生效，脚本和远程单命令调用不受影响，它防的是手滑，不是权限漏洞。
- 禁用 rm 的方案要和回收站清理脚本配套，否则 /data/recycleDir/ 只进不出，早晚撑爆磁盘。
- 清理周期确认用 `-mmin +N`（分钟）还是 `-mtime +N`（天），两者语义差一个量级。
- `sudo rm` 不经过当前 shell 的 alias 展开，拦截对 sudo 调用同样无效。
- 改 /etc/profile 影响所有用户，测试无误再下发到生产。

## 小结

回到开场的 `rm -rf`：alias 拦截让它发不出去，rmf 保险删除留一道确认，回收站加定时清理兜住"真要删"的场景——三层下来，手滑的代价从"一整块数据盘"降为"去回收站捞一下"。两处实测修正（`/bin/rm -i`、`-mmin +2880`）记得同步进你的脚本，方案才真正闭环。
