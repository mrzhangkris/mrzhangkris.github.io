## 一、agent 检索的两个先天短板

让 AI agent 自己上网查资料，你会发现它有两个绕不开的短板。第一是**覆盖面**：通用搜索引擎的网页池里，几乎搜不到 V2EX 上关于「独立开发者怎么定义」的真实讨论、Reddit 上某个库的槽点、arXiv 上三天前的论文——一手信号散落在十几个垂直社区里，每个都有自己的入口和反爬策略。第二是**可信度**：agent 拿到搜索结果往往直接引用，可单次搜索的结果没有经过任何验证，把 SEO 聚合页和 AI 生成的垃圾当成事实转述给用户，是这类链路最常见的翻车方式。

search 这个技能就是为了补这两个短板设计的。它现在以 MIT 协议开源，既可以当独立的搜索 CLI 用，也可以作为 Agent 技能挂载。SKILL.md 里那句自我定义是理解整个设计的钥匙：**「搜索只是发现，深挖才是情报」**——它不满足于返回一页链接，而是把「发现」之后的多源交叉验证、评分、置信度标注全部做进了流水线。这篇文章讲它的设计：引擎怎么组织、降级怎么做、输出为什么长成那个形状，以及它作为开源作品集的定位。

## 二、总体形状：7 阶段流水线

先看全景。一次深挖检索从查询进入，经过七个阶段：意图识别与查询改写 → （深挖模式）查询规划 → 垂直平台搜索 → 并发抓取评分 → 去重与置信度标注 → 交叉验证与矛盾检测 → 情报报告。

这个顺序藏着一条设计主线：**越靠前的阶段越便宜，越靠后的阶段越贵**。意图识别是「规则 + LLM」，LLM 缺位时规则兜底；查询规划只在 `--deep` 模式出现，用 LLM 把一个问题拆成多个子问题再并行搜索；交叉验证和 Deep Research 放在最后，因为它们要调付费模型——SKILL.md 里为此专门写了红线：「本模式调用付费模型、消耗 API 额度——先向用户确认再跑，别静默触发」。agent 技能替人花钱这件事，必须显式过一道用户的闸门。

垂直平台的组织方式是注册表模式：`scripts/platforms/` 下每个平台一个模块，统一实现 `search_platform`（平台搜索）和 `fetch_detail`（抓取接管）两个接口，加 `_base`/`_api`/`_browser` 三个基类做分层复用，注册表自动发现。新增平台的清单在 SKILL.md 里写成了三步：platforms/ 建模块调 `register()`、intent.py 的路由表登记、cli.py 加旗标。旗标数量随平台增长，文档间已经出现了 11 个还是 12 个的口径差——技能自己的处理方式很务实：SKILL.md 明确声明「平台旗标以 `./search --help` 为权威」。文档承认自己会过期，把权威交给代码，这比硬维护一个必然漂移的数字诚实。

## 三、引擎降级链：每一层都有存在理由

通用引擎侧是一条五级降级链：SearXNG（本地 127.0.0.1:8888，聚合 140+ 引擎）→ DDGS → DDG HTML → Bing → Startpage。

这条链的排序逻辑值得看一眼。SearXNG 排第一不是因为它是「最好的搜索引擎」，而是因为它是**聚合器**——一个本地实例背后挂着一百多个上游引擎，任何单引擎被风控都影响有限。但它是自建服务，会挂；于是后面四层全是无状态的 pip 包或直接 HTTP 抓取。有个细节能看出这条链的来历：DDG HTML、Bing、Startpage 三个兜底引擎的说明里写着「蒸馏自 SearXNG duckduckgo.py / bing.py / startpage.py」——兜底实现直接从 SearXNG 的引擎适配代码里蒸馏出来，保证了降级后解析逻辑的一致性。

抓取侧是另一条独立的四级反爬降级链：Scrapling（curl_cffi 指纹）→ StealthyFetcher（camoufox 真人浏览器指纹）→ CloakBrowser（源码级反检测）→ Playwright + Cookie。这些可选依赖缺失时自动跳过对应层，不阻塞安装。

**LLM 能力的降级是第三条线，也是最容易被忽略的一条**。模型与密钥一律不写进技能——`model_caller.py` 被明确要求「零模型名/零密钥」，模型 ID、base URL、API key 全部走 `SEARCH_MODEL_ID` / `SEARCH_BASE_URL` / `SEARCH_API_KEY` 环境变量注入。三者缺任一，LLM 功能自动降级：意图识别退回规则分类、去重跳过 LLM 判重退回文本比对（URL 精确匹配 + 标题归一化），核心搜索链路完全不受影响。这让技能在「裸机环境」和「满配环境」之间是连续过渡的，而不是「配置不对直接不能用」。

## 四、Reddit 403：一条退化路径的完整解剖

降级设计最容易停留在架构图上，拿一条真实路径逐行看才见真章。Reddit 是垂直平台里最有代表性的：它的 JSON API（`reddit.com/search.json`）匿名可用，但对数据中心 IP 和高频请求会直接回 403。

`platforms/reddit.py` 的处理分三段。正常路径走 `build_api_url` 拼 JSON API、`parse_response` 解出标题、subreddit、点赞数、评论数、正文摘要。一旦 `_on_http_error` 捕获到 `HTTPError` 且 `e.code == 403`，走降级：调 `_reddit_metasearch_fallback`，把查询改写成 `site:reddit.com <query>` 交给通用引擎层去搜——**平台丢了，就用通用引擎把平台的域名圈回来**。如果 metasearch 也失败（stderr 打一条「降级也失败」），返回空列表，不抛异常。

这条路径最有价值的地方在结果标记上：降级产出的条目 `engine` 字段标 `reddit_metasearch`（正常是 `reddit_api`），外层检测到首条条目是这个标记时，把整次结果的 `source` 字段改写为 `reddit_metasearch`。**降级不是静默的——下游拿到的每一条数据都自带「它从哪条路径来」的指纹**。点赞数、评论数这些 JSON API 才有的结构化信号在 metasearch 路径里消失了，取而代之的是普通网页摘要——这个信息损失也被字段差异诚实地表达了。

配套的还有知识积累：`domain_knowledge.py` 维护一个域名知识库，把每个域名的抓取方式、反爬类型、信号类型自动记下来，下次直接选最优路径；读写遵循两级回退（优先调用者工作目录，无则回退技能自带目录）。降级是即时止损，知识库是长期少降级——两件事拼在一起才完整。

## 五、输出为什么长这样：为下游 agent 而设计

search 的输出结构，每一处都对准了「下游是另一个 AI」这个前提。

**五维评分带权重与锚点**。信息密度 30%、相关性 25%、独特性 20%、时效性 15%、权威性 10%，每个维度给了 0/50/100 分的行为锚点（比如时效性 100 分 = 正文含当年年份，0 分 = 正文无任何年份）。锚点的意义是让评分可复算——下游 agent 或人可以对着锚点核查一个分数给得对不对。

**来源置信度分 Tier 随结果输出**。T1 权威一手（官方文档、同行评审、标准组织）、T2 高质量二手（知名媒体、高票社区问答）、T3 需验证（论坛、个人博客、社交平台），另有「无署名营销页、SEO 聚合」标记为自动降权——注意是标记降权而非直接丢弃，判定权留给下游。`source_tier` 字段直接进 JSON，报告里显示为 T1/T2/T3。

**交叉验证有硬规则**。每条内容经多次独立验证：前 1-3 次验证得中期评分（±10 浮动），第 4-5 次得最终评分（±15）；3 个以上独立来源指向同一信号，强制升到 60 分以上。去重上，LLM 判 title+snippet 重复对，LLM 不可用时文本兜底，同一 URL、相似度超 80%、同域子页面只计一次。

**异见检索是点睛的一笔**。交叉验证阶段会自动构造对立查询（中文补「批评 缺点 争议」，英文补 criticism/problems/controversy），这是 Munger 反演——「反过来想，总是反过来想」。对立来源最多收录 2 条，写入 `opposition_sources` / `opposition_note` 字段，**不参与加分，只供人工判断**。让 agent 主动去找「我的结论可能是错的」的证据，又不让这类内容污染正向评分——两条规则缺一不可。

**证据纪律管住最后一步**。技术调研场景下，每条断言必须写齐五要素：声明、源、版本、置信度、剩余不确定；缺任一就降级为 `unverified`，不得进结论摘要。版本敏感规则（有 lockfile 就按锁定版本查文档，不脑补升级）和证据优先级（本地源码 > 官方参考 > 迁移说明 > 标准 > 一手研究，搜索页和 AI 摘要不得做主证据）一起，构成从「搜到」到「敢说」之间的完整防线。

## 六、开源作品集的定位

这个仓库的定位不止是一个工具，它是我 AI 工程作品集里的检索方向代表作。为此仓库里放了三样超越代码本身的东西。

**评测样例**。`test-prompts.json` 里五条 prompt，前三条测该触发的场景（对比调研、趋势追踪、框架调研），第四条测付费模式必须先确认的行为约束，第五条是反例——「直接给我 tushare 的官网地址」必须**不**触发技能。把「不该触发」写成测试用例，是 agent 技能评测里最常缺的一块。

**自我进化机制**。`.evolution/` 目录存着一套技能迭代基建：config 里定义了 round_cap（500 轮上限）、acceptance 质量门（真实查询的命中率/召回率不降 + 回归基线 100%）、hard-anchor 防回归锚点，甚至给 design/implement/analysis 不同阶段分配了不同模型。配套的 bench 基线、case 卡片（bloom-filter-refine、relevance-guardrail）意味着这个技能的每次改动都有回归护栏——技能不是写完就冻结的资产，而是带测试基建持续演化的系统。

**权限契约**。SKILL.md 里写明：模型可调用执行，但修改技能代码需先经用户确认；运行时数据（域名知识库、搜索历史、cookie 缓存）的读写位置和降级行为逐项列清。健康检查 `--doctor` 把引擎、依赖、cookie、模型四类前置一次验完。这些不是功能，是**这个技能可以放心交给别的 agent 使用的前提**。

从作品集的角度，它和 dsh 插件系列互补：dsh 系列展示的是「宿主插件怎么设计」，search 展示的是「agent 的能力怎么做成可独立开源、可评测、可演化的技能」。两者共享同一套底层价值观——契约要显式，降级要诚实，证据要可追溯。

## 七、还没解决的事

三个诚实的边界。其一，SearXNG 这条腿是体验的下限：本地实例挂掉时引擎质量显著下降，而它偏偏依赖 Docker 或自管进程，部署面比纯 pip 依赖宽——降级链能兜住可用性，兜不住质量。其二，小红书、知乎、Twitter 这类登录态平台的 cookie 提取天然脆弱，站点一改前端策略就要人工跟进，这块目前没有自动化巡检。其三，交叉验证的「独立来源」判定目前主要靠域名与内容相似度，同一篇通稿被三十个站点转载仍可能被数成三十个「独立源」——语义级的来源同源性识别还没做。

工具在演化，但设计里不变的那条线可以提前写下：**检索的终点不是结果列表，而是下游敢直接引用的那份判断**。
