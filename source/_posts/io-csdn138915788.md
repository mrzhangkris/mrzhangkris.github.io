服务器磁盘 IO 上不去时，先别急着换硬件——调度器、挂载参数、写缓存这些软件层面的调整往往就有明显收益。这篇记录 CentOS 下机械硬盘（HDD）和固态硬盘（SSD）各自的优化点，其中调度器和 LVM 流程在 Rocky 9 容器里实跑验证过，命令和配置可以直接对照改。

## 实验环境

- Rocky 9 容器（一次性 `docker run`，内核 5.14，lvm2-2.03、e2fsprogs 1.46.5）；
- 原文基于 CentOS 7，两代内核的差异会在对应位置标明；
- `hdparm` 写缓存涉及真实 ATA 盘，容器无法模拟，未实跑。

## 先搞清楚盘的类型

两种盘的瓶颈完全不同，优化手段也不同，混着套用会出问题：

- **HDD 的瓶颈在旋转延迟和寻道时间**，物理结构决定了它怕随机读写——磁头跳来跳去的时间远多于真正读写的时间。
- **SSD 靠电子存取，没有机械部件**，速度快得多，但有写入寿命限制，且删除数据需要先"擦"后"写"，这引出了下面的 TRIM。

一句话记住分工：给 HDD 减少寻道，给 SSD 减少无谓写入。

## 实例一：给 SSD 选支持 TRIM 的文件系统

TRIM 是操作系统告诉 SSD"哪些块已经作废"的机制，SSD 据此回收失效块，延缓性能衰减、延长寿命。ext4 和 XFS 都支持 TRIM，SSD 推荐二者之一：

```bash
# 把 SSD 格式化为 ext4
mkfs.ext4 /dev/sda1
```

日常使用建议在 fstab 挂载选项里加 `discard`（持续 TRIM），或者用定时任务跑 `fstrim`——二选一即可。

## 实例二：按盘类型选 I/O 调度器

调度器决定"多个 IO 请求以什么顺序、什么并发度发给盘"。CentOS 7 提供了 deadline、cfq、noop 等，选型思路是：

- **HDD 用 deadline**：给请求设期限，压缩平均等待时间，对大量并发 IO 更友好；
- **SSD 用 noop 或 deadline**：SSD 没有寻道开销，不需要复杂的请求重排，简单的调度逻辑反而省 CPU。

```bash
# 让 SSD 用 noop 调度器（CentOS 7 写法）
echo noop > /sys/block/sda/queue/scheduler
```

这条是运行时生效，重启会丢，持久化要写进 udev 规则或内核参数。

**这里有一个版本坑，实测给大家看。**新内核（5.0 起）移除了 cfq，noop 也被合并进了 none。Rocky 9 容器里查看当前可选的调度器：

![配图2](/images/csdn/figures/io-csdn138915788-2.png)

方括号 `[mq-deadline]` 是当前生效项，可选列表里**根本没有 noop 和 cfq**。所以在新系统上照搬旧教程 `echo noop > ...` 会直接无效——正确做法是 `echo mq-deadline`（HDD、通用负载）或 `echo none`（SSD，让多队列直接处理请求）。CentOS 7 的机器按原文写法即可。

## 实例三：打开 HDD 的写缓存

写缓存把写入先落进盘上的缓存再慢慢刷盘，对 HDD 的写性能提升很直接：

```bash
hdparm -W 1 /dev/sda
```

代价是掉电时缓存里没来得及刷的数据会丢——对数据安全性要求高的场景要权衡，数据库服务器通常宁可关掉它。

> 注：此命令未实跑（需要真实 ATA 盘，容器无法模拟），用法来自原文与 hdparm(8) 手册。

## 实例四：挂载时加 noatime

Linux 默认每次读文件都会更新访问时间（atime），也就是说**读操作其实也在产生写**。挂载时加 `noatime` 可以砍掉这部分开销，HDD 和 SSD 都适用：

```
# /etc/fstab 示例，为分区加 noatime
/dev/sda1 / ext4 defaults,noatime 0 0
```

改动后 `mount -o remount /` 立即生效，不需要重启。

## 进阶：RAID 与 LVM 缓存

对读写性能要求高的应用，可以把盘组成 RAID 10，兼得可靠性和性能。

混合环境（SSD + HDD 共存）下，更省钱的办法是用 LVM 的缓存功能，拿 SSD 给 HDD 当加速层。整体流程是先建物理卷和卷组，再划出数据卷和缓存卷，最后绑定：

```bash
# 创建 LVM 物理卷
pvcreate /dev/sdb
pvcreate /dev/sdc

# 创建卷组
vgcreate vg0 /dev/sdb /dev/sdc

# 创建数据卷和缓存卷
lvcreate -L 100G -n data vg0
lvcreate -L 10G -n cache vg0

# 把缓存卷挂到数据卷上
lvconvert --type cache --cachevol cache vg0/data
```

前面几步在容器里实跑验证过（两个 loop 盘代替 sdb/sdc，lvm2 2.03）：

![配图3](/images/csdn/figures/io-csdn138915788-3.png)

热数据会被 LVM 自动搬到 SSD 那一层，HDD 提供大容量，SSD 提供速度，对应用完全透明。

> 注：最后一步 `lvconvert` 缓存绑定依赖内核 dm-cache 模块，实验容器（Docker Desktop 虚拟机）的内核未包含该模块，未能跑通，此命令按 LVM 官方 cachevol 用法保留，未实跑。真实服务器（CentOS 7.5+ / Rocky 9）内核自带 dm-cache。

## 注意事项

- **动磁盘配置前先备份**，调度器和缓存参数改错了轻则性能变差，重则丢数据。
- **优化参数要结合自己的硬件和业务负载调整**，别人的配置只能当起点。
- **写缓存和调度器这类运行时修改重启就失效**，上线前确认持久化方案。
- **改完要持续观察优化效果**，确认收益是真实的再收尾——iostat、sar 看趋势，别凭感觉。

## 小结

回到开头的场景：IO 上不去，先分清手里是 HDD 还是 SSD——HDD 靠调度器和写缓存减少机械动作，SSD 靠 TRIM 和 noatime 减少无谓写入，混合环境用 LVM 缓存把两边的长处拼起来。改完别忘了两件事：运行时参数要持久化，效果要用 iostat 验证。软件层面榨干之后还不够，再谈换硬件。
