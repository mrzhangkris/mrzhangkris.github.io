## 一、一次契约审查，揪出四个断点

2026 年 9 月 3 日，我们对本机 dsh profile 里一套协同工作的插件做了一次跨件联动契约审查：organ（跨会话记忆）、xirang（息壤，技能进化）、suiren（燧人，经验留痕）加上台账脚本，外加 profile 的实际 patch 配置。审查的结论先行：**主链上有四个真实断点**——台账六检红灯锁死 xirang 全部回写、蒸馏目录被拼出一条永远扫不到的死路径、燧人文档里教的调用参数在 organ 里根本不存在、另有三个工作区的记忆库完全不在扫描范围内。

四个断点有个共同点：**每一个单看都「应该能工作」**。表列契约对齐、文件路径存在、参数名看起来合理、配置项也配了。它们是在插件与插件的接缝上断掉的——A 插件承诺的形状，B 插件理解的形状，两边从未真正对过表。

这篇文章把这次审查连同此前沉淀的调试经验整理成文：先讲 dsh 插件之间到底以什么方式通信，再拆 rpc-bridge 的桥接模型，然后逐个看四个断点的证据与修法，最后是排错方法的沉淀。

## 二、插件间通信的四种形态：没有总线，只有契约

先纠正一个直觉。dsh 的插件之间**没有一条插件到插件的直接消息总线**——cordis 的设计是服务容器加类型化事件，插件通过 `ctx.<key>` 找到别的服务、通过事件观察别的服务，但这些都是进程内的、宿主侧的机制。当我們说「organ 和 xirang 在通信」时，实际的通信形态要琐碎得多，本机这套链路里能数出四种：

**共享持久层**。organ 把记忆写进 `<workspace>/.dsh-organ/memory.db`（SQLite WAL），xirang 以只读方式 SELECT 同一个库的 `lesson` 和 `topic` 表。这是最强的契约：表名、列名、状态过滤条件（`WHERE status != 'archived'`）任何一侧变更，另一侧立刻断。审查确认表列契约是对齐的，`queue.jsonl` 里 14 条真实信号也证明这条数据流工作过。

**工具调用契约**。燧人（一个技能，由模型执行）按它 SKILL.md 里写的方法签名调 `organ_remember` 工具。这个契约有三层：文档教的写法、organ 工具层声明的 JSON Schema、organ 内部实现真正读取的字段。三层中任何一层和另外两层不一致就是断点——后面会看到，`corrected` 参数恰恰断在最深处。

**HTTP 端点**。开发工具（比如 MCP server）要调用宿主服务时，走 dsh-rpc-bridge 插件在 dsh-web 上注册的 HTTP 端点。这是唯一一种「活进程对活进程」的调用，也是本文第三节的主体。

**文档与目录约定**。organ 把蒸馏产物写到 `~/.dsh/skills/organ-distilled/<name>/SKILL.md`，xirang 负责扫描这个目录触发登记；台账脚本按 LEDGER.md 约定的状态机读写 `~/.dsh/ledgers/state/` 下的 yml。这类契约没有代码强制，全靠两侧对「目录长什么样」的想象一致——死路径断点就出在这里。

四种形态共享一个特征：**契约的 enforcement 分散在不同强度的地方**——JSON Schema 会硬报错，目录结构没人查，文档更是纯自觉。跨件联动的坑，几乎都埋在 enforcement 最弱的那些层。

## 三、rpc-bridge：把宿主服务的方法变成一个 HTTP 调用

rpc-bridge 要解决的问题很具体：宿主进程里已经有一批服务对象（agentPresets、settings、sessions 控制器），宿主内插件通过 `ctx.get` 就能调它们的方法；但**进程外的开发工具**——MCP server、脚本、AI 助手——没有任何入口碰到这些方法。bridge 的做法是把「宿主内调用」原样搬到一个 HTTP 端点上。

它的 patch 声明只有三行——`insert` 一个 id 为 `dsh-rpc-bridge` 的条目——但实现里有几个值得细看的设计：

**Remote 方法就是 cordis 服务的普通方法**。请求体是 `{ns, method, args}` 三个字段：`ns` 是服务名（支持 `agentPresets` 这样的服务 key，也支持 `agent-presets` 这样的 namespace，桥会自动驼峰化后回退尝试），`method` 就是服务对象上的方法名，`args` 是位置参数数组，按 Remote 方法签名顺序展开。调用直接从 registry 取实例后展开参数——没有另一套 RPC 协议，没有序列化 schema，宿主方法签名即接口文档。

**错误消息带方法目录**。`method` 名对不上时，桥返回 404 并附上 `available` 字段——该服务对象上所有函数方法名（截前 30 个）。这个设计在消费侧（dsh-dev MCP 的 `dsh_rpc_call`）被写进了工具描述：「method 名不对时错误信息会列出可用方法」。AI 拿到一次 404 就能自我纠正，不需要人翻源码。

**晚绑定补挂**。bridge 的 `apply` 执行时 webServer 服务未必就绪，它每秒重试一次注册、最多 30 次，同时监听 `internal/service` 事件触发补挂——注释里标注这是「pruner 同款模式」。这是 cordis 生态里处理服务启动顺序不确定性的通用姿势：不假设顺序，轮询加事件双保险。

**边界刻意收窄**：只支持无 lookup 参数的方法（需要 Agent 等宿主对象做参数解析的方法直接明确报错，不猜）；AbortSignal 不自动注入（查询类方法无需取消）；请求体上限 1MB；端点在 dsh-web 之上受同一 token/cookie 鉴权保护。bridge 定位是本机开发工具通道——仅 127.0.0.1，不对外。

这个桥的另一半价值在消费侧的分工：dsh-dev MCP 的 `dsh_rpc_call` 只管认证和转发，协议细节全部留在 bridge 侧。桥不翻译语义、不维护白名单，能力面严格等于 bridge 暴露的服务面——**接缝处只留一层职责，是这类工具能长期不腐烂的关键**。

## 四、四个断点：证据、后果、修法

回到 9 月 3 日的审查。四个红灯逐个看。

**断点一：六检红灯锁死全部回写。** 症状是 xirang 对台账的一切写入（backlog 追加、货架终态、verify 登记）被静默拒绝。追下去的证据链：organ 上线后磁盘上出现了 `organ-distilled/` 这个容器目录，台账的磁盘对账脚本 `ledger-check.py` 把它当成了一个未登记的技能目录，判「漏记」，六检基线变红；而 xirang 的 `atomicWriteGuarded` 遵循「基线红即拒绝写入」的纪律，只打 warn 不落盘。**对账工具本意是防数据损坏，结果自己的误报卡死了整条业务链**——从 `organ-distilled` 目录出现那天起，回写就停摆了。修法出奇地便宜：对账排除该容器目录（与既有 `scripts` 豁免同款），一行改动，六检变绿后回写自动恢复。

**断点二：蒸馏目录的死路径。** organ 的产物根 `~/.dsh/skills/organ-distilled` 下面直接就是 `<name>/SKILL.md` 的结构——产物根本身就是技能目录。而 xirang 的扫描逻辑假设根目录下还有一层 `.agents/skills`，不匹配就拼上去，于是实际扫描的是 `organ-distilled/.agents/skills/`——一个不存在的路径，实测确认，扫描结果永远为零。organ 明明已经落地产物，登记链却从未被触发。最难受的是修法绕不开配置：审查明确写了「任何不以 `.agents/skills` 结尾的写法都会被拼死」，只能改代码——要么扫描逻辑支持「根直扫」探测（任一直接子目录含 SKILL.md 即视为技能根），要么把这个布局识别为第④种合法写法。

**断点三：文档教的参数不存在。** 燧人的 SKILL.md 第 51 行教模型这样留痕：`organ_remember(level=lesson, corrected=true, project=…)`。而 organ 工具层的参数 Schema 里没有 `corrected`，且声明了 `additionalProperties: false`——dsh 的工具值校验对未声明属性直接报 `"corrected" is not a declared property`。**按文档调用，第一次必失败**，全靠模型自愈式地把参数去掉才可能成功。更深一层：organ 全链路都没有 corrected 的写入口，`writeMemory` 的 merge 不更新它，数据层的 `lesson.corrected` 恒为 0——「被纠正」这个语义在设计里就丢了。修法两边都能做：文档删掉这个参数（一行），或者 organ 真的把它实现出来。

**断点四：单库盲区。** organ 是 per-workspace 建库，每个工作区一份 `memory.db`。实测磁盘上有三个活跃库：开发 70 条 lesson、探索 26 条、临时工作区 48 条——合计 144 条记忆里，xirang 因为配置里 `memoryDbPath` 硬编码单库，只扫得到「开发」那 70 条。「工作区 A 里燧人记了改进点，息壤永远看不到」——多工作区这个使用现实，把单库假设击穿了。修法是让 `memoryDbPath` 支持数组多库扫描（表结构同构，循环拉取即可）。

## 五、契约坑的共同模式

四个断点摆在一起，能提炼出几个反复出现的模式。

**文档跑在实现前面**。`corrected` 参数是文档里写了、Schema 里没有、实现里更没有——三层中只有最虚的一层存在。技能文档由模型执行，模型是文档最忠实的用户：文档教错，它就按错的调。这类坑的检查方法很简单：**文档里每个调用示例，都要能对着工具 Schema 逐参数核对**。

**路径拼装的隐式假设**。死路径的本质是一侧假设「技能根长这样」，另一侧的产物「长成那样」，两侧的想象从未对表。目录契约没有 Schema 也没有校验，只能靠审查或实测发现——审查报告里那句「已实地验证」比任何推理都有力。

**守护机制误伤业务**。六检的纪律（基线红拒绝写入）本身是对的，错的是对账误报。但组合起来的效果是：一个与业务毫不相干的容器目录命名，就让整条结算链停摆。**守护机制的误报不是警告，是停机**——凡是「校验不过就不干活」的链路，校验器的误报必须按 P0 处理。

**作用域假设落后于使用现实**。单库假设在建库时是对的，多工作区成为常态后就过期了。这类契约坑最隐蔽，因为它不报错、不断链，只是**静默地丢一半输入**——75 条 lesson 沉默，没有任何日志会告诉你。

## 六、调试经验的沉淀：从症状到日志

契约审查能发现问题，靠的是之前反复排错攒下的方法。几条最值钱的：

**先分半区，再动手**。症状在 client（浏览器侧 bundle、面板）还是 host（工具调用、turn 失败）还是配置层（根本没进组合树），排查入口完全不同。配置层一句话定性：`dsh --profile web --dump-config | grep <插件名>`——没进组合树，后面全白搭。

**client 侧的失败在 server 日志里零痕迹**。client 激活失败只出现在浏览器 console——这是硬知识，不知道它的人会在 server 日志里翻一天。

**会话日志是最强证据源**。`~/.dsh/sessions/` 下 zstd 压缩的 `session.jsonl` 解开后，`turn/end` 的 reason 字段直接区分故障来源：`aborted` 加 `disposed` 是 server 重启或插件 fiber 被杀，`interrupted` 是外部中断，`error` 才是 turn 级异常。还要警惕前端显示的合成结果——工具行里那句 `Interrupted` 是前端在 turn 被 abort 后对未完成调用补写的，不是工具自己报错。**别把 UI 的善意提示当证据。**

**ctx 白名单 Proxy 之痛**。cordis 的 ctx 是 inject 白名单的 Proxy，访问任何未在 inject 数组里声明的属性直接抛 `cannot get property "X" without inject`——不存在「防御性读一下」这种操作。xirang 曾因为预检代码里读了 `ctx.disposed`（cordis 里根本不存在的属性）每轮调度都在函数头几行炸掉，而异常又被 catch 吞掉、logger 输出不知去向，整整停摆三天。解法事后看极其朴素：**关键 catch 里加 `console.error`，让 stderr 直写 guard 日志**。那条复盘的原话值得刻在墙上：纸面推演三天，不如一条 stderr。

**判据要选不可伪造的证据**。用文件 mtime 判活会被启动时的 saveAll 骗过（假活）；判活要看只有目标链路真跑过才会更新的字段（比如 triage 的 checkpoint）。同理，mock 环境复现通过不等于生产正常——mock 的普通对象随便加属性，真 ctx 的 Proxy 会炸；单插件 mock 全绿的教训在跨件场景只会放大。

## 七、还没收的尾

审查报告里还有几件事没闭环：flock 持锁范围不含读操作（读-改-写在锁外，与结算脚本并发存在丢更新窗口）、lesson 的 stale 标记归属真空（没人打，只能靠指纹去重兜底）、燧人文档引用的 pool-export 脚本全盘失踪。三个都是小改动，但都还没改。

更大的一个开放问题是：跨件契约目前靠「人发起审查」才被检查，四个断点里最贵的那个（单库盲区）存在了多久已经无从考证。契约审查本身能不能变成插件链路的常设巡检——像六检对账数据那样对账契约——是下一步值得想的事。毕竟这次审查证明了：**接缝上的问题，接缝自己的视角才看得见。**
