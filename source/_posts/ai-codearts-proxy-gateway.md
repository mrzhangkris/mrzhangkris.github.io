## 一、额度在三家，接口在四处

我本机的编码 agent 靠各家免费额度过活，手里攒了三个来源：华为云 CodeArts 的开发者计划，标注每日 1000 万 tokens，模型目录里有 1M 上下文的 glm-5.3-flash 和 deepseek-v4 系列；腾讯 CodeBuddy 中国版；腾讯 WorkBuddy 国际版，模型池里是 GPT-5.6、Gemini-3.5、Kimi-K3 这一挂。

额度是真的，用起来也是真的麻烦。三家的入口各管各的：CodeArts 说 Anthropic 的 Messages 协议，CodeBuddy 是 OpenAI 兼容接口但圈在自家生态里，WorkBuddy 又是另一个站、另一套账号。而 agent 侧只认两样东西：一个 base URL，一个 API key。每接一家改一遍配置，每家断供单独排查，账没法算。

codearts-proxy 是给这个局面的答案：一个零依赖的 Node 22 ESM 服务，launchd 常驻，8799 端口，把三家后端翻译成四个命名空间：

| 路由 | 后端 | 说明 |
|---|---|---|
| POST /v1/messages | 华为云 CodeArts | 原生 Anthropic Messages |
| POST /v1/chat/completions | 腾讯 CodeBuddy | OpenAI 兼容 |
| POST /wb/v1/chat/completions | WorkBuddy 国际版 | OpenAI 兼容 |
| POST /wb/v1/messages | WorkBuddy（桥接） | Anthropic 形态，内部转 OpenAI |

每个命名空间各配 GET /models。客户端侧，任何支持自定义 provider 的工具，base URL 填 127.0.0.1:8799、API key 填一个本地口令就完事。我这边的接法是接管配置里一个闲置的内置 provider，把 baseURL 指到代理，再把 GLM-5.3 别名映射到 glm-5.3-flash——本文草稿用的模型，走的就是这条链路。

凭证的分工值得单独说。三家账号的登录、token 续期、多账号池，由上游的 dsh-codearts-auth 插件（gitee 上的开源项目）负责，凭证落在一个 yaml 文件里；代理是纯只读消费者，监听文件 mtime 热加载，自己绝不刷新 token。凭证生命周期和流量翻译拆成两件事，出了问题立刻知道该怪谁。

## 二、腾讯后端的三条规矩

三家后端里腾讯系最挑。三条规矩都是拿真实 400 码换来的：

第一，只收流式。非 stream 请求直接 400，错误码 11101。但很多调用方要的是一次性 JSON。代理替你收流：后台把 SSE 分片攒完，聚合成完整响应再返回，调用方感知不到对方只肯说流式。

第二，第一条消息必须是 system 角色，否则 400 码 11128。有些客户端的对话从 user 开场，代理检测到就注入一条占位 system。两行代码的事，但你得先撞过一次才知道。

第三，tool_choice 只认字符串。传对象形态（`{"type":"auto"}` 这种 OpenAI 标准写法），Go 写的腾讯后端直接报 `cannot unmarshal object into Go struct field Request.tool_choice of type string`——标准里合法的写法，在这里过不了关。桥接层统一收敛成字符串再发。

这三条没有一条写在官方文档里，全是对着错误码逆向出来的。协议兼容的工作，做之前以为是翻译，做之后发现是给上游的随意性做减法。

## 三、华为的 64 字符，和一次路由想当然

华为侧的坑形状不同。第一个是工具名长度：CodeArts 后端拒绝超过 64 字符的 tool 名，报 InferHub.001001017.413。这个数字哪来的？MCP 工具的命名规范是 `mcp__plugin_<插件名>_<插件名>__<方法>`，android-emulator 插件的 discover_project 方法拼出来 71 个字符，正好撞线。腾讯后端没这个限制，同一个名字完整往返。目前的解法是绕行而非修复：把重工具的客户端路由到没有长度限制的腾讯桥。

第二个藏在签到协议里。CodeArts 的每日领积分是一条三步链：查活动、领额度、确认入账，少了最后一步积分会停在 pending。更隐蔽的是签名顺序——有两个请求头必须在对整个请求做 HMAC 签名之后追加，混进签名内容里网关直接拒掉。签名覆盖范围这种事文档不写，只能二分排查。

第三个坑出在自己身上。/wb/v1/messages 上线之初被想当然地路由到了华为的 Anthropic 处理器——毕竟它是 Anthropic 形态的。但路径前缀决定"去哪家"，路径形状决定"说什么协议"，这是两个维度，路由表缺一个维度，Anthropic 客户端的请求就会静默落到错误的后端。修法是补全维度：/wb 命名空间下所有方法形状一律进 Anthropic↔OpenAI 桥。

## 四、"通讯失败"其实是没积分了

上线后第一次像样的故障，表象是 WorkBuddy 通道全部报"通讯失败"。按惯性先查代理：进程活着，端口通，/models 正常列模型，key 校验通过——代理这一层什么都是好的。

再往上游抓原始报错，答案在腾讯返回的 error code 14018：Credits exhausted, please purchase add-on packs。上游账号积分用完了，跟代理、网络、鉴权都没关系。签到状态也印证了：WorkBuddy 的签到活动 9 月 20 日之后停开，每天 +100 的补给断了，额度只出不进，耗光是迟早的事。

这次排查留下一条纪律：多层链路里报错，先回答"这个错误属于哪一层"，再动手修。代理转发链上每一层都能产生失败，把上游的业务错误（没积分）和网络错误（连不上）、鉴权错误（key 无效）分开，靠的不是日志措辞，而是拿着 requestId 去上游核对原始响应。客户端 UI 把 14018 翻译成"通讯失败"，是好心，也是误导。

## 五、把每日签到变成无人值守

积分会耗尽，那就让补给自动化。代理内置了签到调度器：启动 10 秒后跑第一轮，之后每 4 小时一轮；当天已领的账号固定跳过，失败和"活动未开启"的留到下一轮再试，新账号自动纳管。配套两个端点：GET /checkin/status 看三家当日状态，POST /checkin/run?force=1 手动补跑。

实现里最值得一提的是幂等判断的取法。腾讯的签到接口，重复领取返回的是 HTTP 400——不能用状态码判断"今天签过了"，只能解析响应体里的业务码，才能区分"已领过""活动未开启""领取成功"这几种结局。HTTP 语义和业务语义在这里是两层，判断要用里层那层。第一次实跑：buddy 领到 +100，codearts 当日已签（回查原始领取记录确认到账），workbuddy 活动未开启，77 个单测全绿。

## 六、风险与没做完的事

先把丑话说完：这套协议不是官方开放的 API，上游插件作者用 mitmproxy 抓包逆向而来，风控策略随时可能变，ToS 层面也有灰色地带。我的用法是个人额度自用、单账号、低频，这个前提说在前面。哪天某家改了协议或收紧风控，这个项目当天就可能报废——薅免费额度的架构，要有薅不到的预案。

没做完的也列出来：华为侧超长工具名的通用缩短映射还没实现，现在靠路由绕行；workbuddy 账号续命只能等签到活动重开或手动充值；三家后端的错误码散落在代码注释里，没整理成对照表。这些不影响主线使用，但离"能交给第二个人用"还差一段。

回头看，这个项目里值钱的不是那几百行转发代码，而是三家后端用真实 400 码教出来的规矩清单。每一行都对应一次真实的失败和一次真实的修正——这份清单本身，比代理更值得留下来。
